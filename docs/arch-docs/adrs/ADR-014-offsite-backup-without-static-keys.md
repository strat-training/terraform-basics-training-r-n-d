# ADR-014: Off-site backup to GCS without static keys

- **Status:** Proposed (needs a build-phase spike before it is final)
- **Date:** 2026-10-01
- **Deciders:** Program owner (@Lee) to confirm
- **PRD references:** s.9 (capstone, GCS bucket for DB backup), s.10 (credentials), s.12 (Prove: "backup present in GCS"; Security: "no static credentials"), s.14

## Context

The capstone must show the database backup present in a Google Cloud Storage bucket after a single apply, with **no keys or secrets in the repository**. The RDS database is private, so something inside the AWS VPC has to produce the dump (the provided `data/db-seed-and-dump.sh` helper), and that something must authenticate to GCP to upload it. A downloaded service-account key would be a static credential and would end up on an instance or in state.

## Decision

Use **GCP Workload Identity Federation** so the App tier's **AWS instance role** authenticates to GCP with short-lived tokens:

1. Terraform creates, in the GCP project: the bucket, a service account with write-only access to that bucket, a workload identity pool and an **AWS provider** that trusts the specific AWS account and the App tier role.
2. Terraform grants the pool principal permission to impersonate the service account.
3. The App tier boot script runs the dump helper after seeding the database and uploads the result to the bucket using a **credential configuration file** (generated by Terraform, containing no secrets) that exchanges the AWS role identity for a GCP token.
4. The bucket has uniform access, no public access, a lifecycle rule to expire old backups and a label set for the clean-up check.

**Spike (weeks 1-2 of the launch plan):** confirm the sandbox project allows creating workload identity pools and that the flow works end to end on the instance. If not, apply the fallback below.

**Fallback (documented, lower fidelity):** produce the dump from `data/seed.sql` on the provisioning host and upload it with `google_storage_bucket_object`. This proves the bucket and the Terraform wiring but not a live backup from the private database; the rubric text for "backup present in GCS" would be adjusted accordingly.

## Alternatives considered

| Option | Why not chosen |
| --- | --- |
| Service-account JSON key stored in Secrets Manager or user data | Static long-lived credential; contradicts the course's central rule and rubric |
| Make RDS publicly reachable and dump from the learner's machine | Violates "database not public" |
| Cloud Storage Transfer or Database Migration Service from GCP side | Needs inbound access to the private RDS; more services than the PRD scope allows |
| AWS Backup with cross-cloud copy | Not supported to GCS; not a Terraform-only pattern |
| Skip live backup, only upload seed file | Becomes the fallback, not the primary design |

## Consequences

**Positive**
- Real cross-cloud, key-free authentication, which is a strong lesson in how clouds trust each other.
- Satisfies the rubric's security criterion without exceptions.

**Negative / trade-offs**
- **Highest technical risk in the capstone**: workload identity federation adds several GCP IAM resources and is the least beginner-friendly part of the course. The module must explain it as "given" scaffolding learners read but do not design, to keep the 7-9 hour budget.
- Requires GCP API enablement (`iam`, `iamcredentials`, `sts`, `storage`) through `google_project_service`, which reinforces the Week 4 lesson but adds apply time and a known eventual-consistency delay; boot script retries are required.
- Depends on sandbox IAM permissions for the learner (create pools, providers, service accounts). Captured in the sandbox contract (ADR-005 follow-up).
- IAM propagation can make the first upload fail; the boot script retries with backoff, and the "prove" step allows a short wait.
